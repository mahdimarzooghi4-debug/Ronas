# Ronas — persisted local authority change journal (LOCAL/TEST)

**Status:** a technical **single-host SQLite reference journal**, not a Production authoritative source, scientific content registry, professional credential service or source-rights engine. Existing Business D1-DATA-01/02, D1-SCI-01, D1-REV-01..04 remain unapproved. Domestic #2, Export #3 and Finance #4 remain OPEN. No credentials, real household evidence, source files, external APIs or payments are introduced.

## Goal and interface

`SqliteSyntheticAuthorityRevisionJournal(path)` persists **source-specific** generation changes for the three exact kinds `SCIENCE_SOURCE_CANDIDATES`, `SPECIALIST_EVIDENCE_CANDIDATES`, and `CASE_ASSIGNMENT` keyed by a DEMO subject, DOMESTIC case ref and pinned case version. The journal stores **only a canonical SHA-256 snapshot digest**, action ID, strictly increasing per-scope generation, a globally sequential append-only event position and linked SHA-256 event chain. It stores no source text, licensing evidence, personal identity document or specialist conflict disclosure.

`record_snapshot(kind,subject,case_ref,case_version,snapshot,action_ref,expected_generation)` is a **LOCAL/TEST internal API**, not HTTP or a real source mutation. All writes serialize in SQLite `BEGIN IMMEDIATE` and use explicit optimistic CAS `expected_generation`; replay of the identical latest action is idempotent, while conflicting/reused/stale action or version reset fails closed. Every read or write re-verifies the append-only global chain, per-scope exact generation continuity, metadata head and triggers; unknown/missing/stale snapshot hashes fail closed. File must be absolute, private 0600, regular and not a symlink. Concurrent writers from two independent instances race safely; only one CAS winner commits. Reopen of the same file preserves generations.

`snapshot_digest` pins actual typed **synthetic** snapshots: sorted `ScientificSourceCandidate` tuples; `SyntheticSpecialistEvidenceRegistry` filtered to the exact specialist and case/version; and an explicit Boolean from the independent live-assignment fixture. `witness_for_snapshot` verifies that the current live synthetic snapshot still hashes to the latest registered state and returns the actual persisted `SyntheticAuthorityWitness`. `callback(kind, snapshot_reader)` exposes that check as a reusable provider callback for the existing opt-in `review-context-versioned` endpoint, only when explicitly wired in LOCAL/TEST. No default application route or new writer is mounted.

An A→B→A series generates **three** persisted generations even if the last snapshot bytes again match the first. The versioned context fingerprint therefore differs and a prior client fingerprint is rejected. Reusing `expected_generation=0` after successful records, skipping values, or tampering stored event rows cannot generate a valid witness.

## Security limits

This journal guarantees only consistency of **its own append-only generation state**; it is NOT yet an atomic persistence layer for the independently configured science fixtures, specialist registry and live assignment authority. If a caller changes the underlying candidate/assignment fixture without writing the corresponding journal event, reading the witness fails closed on snapshot digest mismatch; if the caller intentionally rewrites A→B→A entirely without journaling, no local observation can detect that hidden history. Real providers must update their own data and durable revision **atomically**; the future Production contract and retention/access controls require independent Business approval.

A wholly deleted/recreated database, a sufficiently privileged attacker that rewrites all rows, head and journal triggers consistently, and an unanchored SQLite copy rollback cannot be cryptographically detected by an unkeyed in-DB hash chain alone. No external immutable anchor or secret signature is invented. The local SHA chain detects ordinary edits and missing/tampered rows only within this trust boundary; it must not be marketed as external audit attestation or rollback-proof evidence.

The existing signed-role/live-assigned read, strict source/plan checks, double-observation checks and `NOT_REVIEWED` decision boundaries stay unchanged. No professional qualification, actual science/legal source review, independent conflict clearance, real AI execution, plan approval or Stage/QA/Release/Production.


## Explicit opt-in strict GET integration check

The LOCAL/TEST specialist workspace can receive the `journal.callback(...)` readers as the three `trusted_*_authority_version` callbacks for the already supported `review-context-versioned` route. The signed, live-assigned endpoint still checks its existing independent proposal/source/specialist/current-case state and the same append-only case journal. Integration tests now reopen the witness journal in a second instance, supply actual persisted witness callbacks, verify a current read, record A→B→A separately in each provider scope, and confirm the prior versioned context token is rejected while the structural context stays unchanged. An unjournaled fixture mutation or a tampered witness journal returns generic 503 and no successful read audit. This bridge is test configuration, NOT a new HTTP writer and not an assertion that the source, specialist, or assignment fixture mutation is atomically persisted with its witness event.
