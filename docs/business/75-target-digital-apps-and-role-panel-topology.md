## ۱. نتیجه الزام‌آورِ تصمیم کارفرما: نقش و پنل

**پنج نقش بیرونی دارای نمای کاربری، یک پنل ستاد مشترک با چهار حوزه حق دسترسی، یک اتصال API مستقل بدون پنل، چهار پنل قبلی حذف شده‌اند.** «پنج + یک» برابر شش **فضای تجربه** است، نه شش اپلیکیشن یا شش سرویس.

| ردیف از ۱۴ مورد قبلی | نقش/گروه | نتیجه تصمیم کارفرما | تجربه باقی‌مانده |
| --- | --- | --- | --- |
| **۱** | خانوار / تولیدکننده خانگی | **KEEP** | نمای خانوار/کشت و برداشت؛ فروش مشروط، نه فعال |
| **۲** | خریدار محلی | **KEEP** | نمای خریدار؛ بازار و سفارش فقط بعد از گیت Domestic، کیفیت و Finance |
| **۳** | کارشناس کشاورزی | **KEEP** | نمای متخصص واقعی؛ بررسی داده و تأیید/بازنگری برنامه کشت، نه تأیید خودکار AI |
| **۴** | فروشنده تجهیزات | **KEEP** | نمای فروشنده تجهیزات؛ هیچ قرارداد فروش/قیمت/پرداخت اختراع نمی‌شود |
| **۵** | هاب/پیک محلی | **API INTEGRATION ONLY — NO PANEL** | فقط قرارداد اتصال بیرونیِ آینده، وابسته به شریک واقعی، احراز سرویس و شواهد |
| **۶** | کارشناس مستقل QC/فرآوری | **REMOVE DEDICATED PANEL** | الزام حقوقی/علمی کنترل کیفیت حذف نمی‌شود؛ شیوه وصول گواهی معتبر/کارشناس مجاز هنوز OPEN |
| **۷** | تأمین‌کننده حرفه‌ای Export | **KEEP** | نمای تأمین‌کننده حرفه‌ای؛ ظرفیت ادعایی ≠ قرارداد یا خرید |
| **۸** | کارشناس مستقل تجارت و صادرات | **REMOVE DEDICATED PANEL** | کارکرد مطالعه E0 و هماهنگی، **در حوزه دسترسی «عملیات صادرات» پنل واحد مدیران**؛ بازبین معتبر شواهد همچنان لازم |
| **۹** | خریدار خارجی | **REMOVE DEDICATED PANEL** | بدون پرتال خریدار خارجی؛ تعامل تجاری احتمالی با قرارداد واقعی/کانال بیرونی، نه API خودکار |
| **۱۰** | مدیر عملیات داخلی | **MERGE** | پنل مدیریت واحد: **دسترسی عملیات Domestic** |
| **۱۱** | مدیر عملیات صادرات | **MERGE** | پنل مدیریت واحد: **دسترسی عملیات Export** |
| **۱۲** | مسئول مالی | **MERGE** | پنل مدیریت واحد: **دسترسی مالی** با جدایی Domestic/هر قرارداد Export |
| **۱۳** | پشتیبانی و مدیریت محتوا | **REMOVE DEDICATED PANEL** | هیچ فضای کار جایگزین، تیم پشتیبانی یا دسترسی انتشار محتوا به‌طور خودکار اضافه نمی‌شود |
| **۱۴** | مدیر کل سامانه | **MERGE** | پنل مدیریت واحد: **دسترسی راهبری/مدیریت**؛ نه دسترسی بی‌قید به اطلاعات/وجوه |

**تعریف دقیق شمارش:** ۵ نمای نقش‌محور بیرونی (۱،۲،۳،۴،۷) + **۱ پنل مدیریت** حاوی ۴ دسته دسترسی (۱۰،۱۱،۱۲،۱۴) = **۶ نمای/پنل در سطح تجربه**. نقش API-only (۵) **بدون پنل** است. موارد ۶،۸،۹،۱۳ **هیچ پنل یا اپ مستقلی ندارند**. وجود چهار حوزه دسترسی داخلی به معنی ساخت چهار پنل جدید نیست.

## ۲. دو محیط کاربری مصوب — RON-DEC-031

در پاسخ به پیشنهاد صریح دو محیط کاربری، کارفرما گفت **«موافقم»**. بنابراین تعداد و مرز **دو پوسته تجربه** در سطح Business **مصوب** است و پیشنهاد قدیمی چهار اپلیکیشن از مبنای طراحی کنار گذاشته می‌شود:

| محیط کاربری مصوب (BUSINESS APPROVED) | ترکیب | هدف |
| --- | --- | --- |
| **«روناس» — رابط مشترک کاربران و همکاران** | ۵ نمای نقش‌های **۱،۲،۳،۴،۷** در یک تجربه پاسخگو با ناوبری و مجوز مبتنی بر نقش و موتور | یک نقطه ورود مشترک بدون حق دسترسی متقابلِ پیش‌فرض؛ انتخاب Native/Web/PWA و تعداد باینری هنوز باز |
| **«مدیریت روناس» — یک پنل ستاد** | نقش‌های **۱۰+۱۱+۱۲+۱۴** در یک پوسته، چهار **بسته مجوز جداگانه** | عملیات Domestic، عملیات Export، امور مالی و راهبری با حدود شواهد/اختیار مستقل |
| **اتصال هاب/پیک** | ردیف **۵** فقط در صورت وجود قرارداد سرویس واقعی | API با هویت سرویس، محدودیت داده/عملیات، اعتبارسنجی و رویداد قابل اثبات؛ **هنوز Endpoint یا Partner واقعی موجود/تصویب نشده** |

این یعنی **دقیقاً دو محیط کاربری در سطح Business تأیید شده‌اند** (یک تجربه کاربران/همکاران و یک پنل مدیریت واحد)، به‌علاوه اتصال API مستقل مشروط برای هاب/پیک. این تصمیم درباره **تعداد و دسته‌بندی تجربه** است، نه تعداد باینری‌های Mobile/وب‌سایت، فریم‌ورک، مخزن کد، دیتابیس، Host، IAM یا امکان پردازش واقعی داده. Technical همچنان برای این موارد ADR مستقل لازم دارد. [نقشه گام‌های نخستین UI/UX بر همین مبنا](76-two-interface-ux-entry-points-and-first-slice-journeys.md). سایت عمومی می‌تواند بخشی از رابط کاربران باشد و اپلیکیشن سوم الزام نمی‌شود.

## ۳. پنل مدیریت واحد با دسترسی‌های متفاوت

| حوزه داخل همان پنل | مجوز موضوعی مورد نظر، نه Rule اجرایی | نباید اتفاق بیفتد |
| --- | --- | --- |
| **ADMIN-DOMESTIC (از ۱۰)** | مشاهده و پیگیری پرونده/استثناهای داخلیِ متعلق به قلمرو مجاز | جایگزینی تأیید علمی متخصص، انتشار مازاد یا قیمت‌گذاری تولیدکننده |
| **ADMIN-EXPORT (از ۱۱ و جایگزین نمای مستقل ۸)** | ثبت/مرور پرونده سؤال پژوهش، منابع، محدودیت و اقدام انسانی؛ پیگیری تأمین/قرارداد در صورت مجوز | تبدیل خودکار Lead/Research به خریدار خارجی واقعی، خرید یا صادرات، یا جعل تأیید پژوهش |
| **ADMIN-FINANCE (از ۱۲)** | گزارش و تطبیق مستندات داخلی و هر قرارداد صادراتی به تفکیک | فعال‌سازی بانک/PSP/FX/Settlement، دسترسی مالی نامحدود یا دوباره‌شماری درآمد |
| **ADMIN-GOVERNANCE (از ۱۴)** | نظارت و تغییر تحت رویه انسانی مصوب، کنترل دسترسی و پیگیری شواهد گیت | تبدیل عنوان «مدیر کل» به مجوز شکست حریم شخصی/اقدامات مالی/تأیید QC یا Crop Plan |

**جایگزینی نقش ۸:** E0-A حذف نشده است؛ فضای پژوهش و هماهنگی‌اش داخل **ADMIN-EXPORT همان پنل مدیریت** قرار می‌گیرد، نه یک نقش یا اپ مستقل. صلاحیت و استقلال بررسی انسانی موردنیاز را نمی‌توان از نام «مدیر صادرات» نتیجه گرفت؛ قبل از استفاده عملیاتی باید مرجع واقعی تعیین شود.

**جایگزینی نقش ۶:** پنل QC حذف است، **خود کیفیت خوراکی و صلاحیت مرجع تأیید باقی می‌ماند**. اگر شواهد کیفیت در آینده لازم باشد، منشأ معتبر بیرونی/بررسی انسانی قانونی به‌صورت مستند دریافت شود؛ پنل جدید یا وضعیت QC PASSED خودکار ایجاد نشود.

**حذف ۹:** Export تجاری می‌تواند بعداً از فرایند قراردادی با طرف خارجی استفاده کند؛ این مصوبه **پرتال یا حساب کاربری خارجی** تعریف نمی‌کند.

**حذف ۱۳:** خدمات پشتیبانی/محتوا را بی‌صدا داخل «مدیر کل» بازسازی نکنید؛ هر نیاز عملیاتی جدید به تصمیم Scope و مجوز نیاز دارد.

## ۵. اثر فوری بر اولویت ساخت و PR #9

- **CORE-D1-A:** «خانوار ۱» نخستین UX اصلی است؛ بررسی/نظارت عملیاتی در **دسترسی ADMIN-DOMESTIC نقش ۱۰ داخل پنل واحد** قرار می‌گیرد. «کارشناس ۳» برای برنامه کشت واقعی CORE-D1-B لازم است، نه برای جعل تأیید در D1-A.
- **CORE-E0-A:** نیاز به پنل کارشناس صادرات مستقل (۸) **حذف شد**؛ UX پژوهش/منابع و بازبینی شواهد داخل **ADMIN-EXPORT نقش ۱۱** طراحی می‌شود. این تغییری در حقوق منابع، بازبین واقعی، منبع‌دار بودن یافته‌ها یا مستقل‌بودن Export ایجاد نمی‌کند.
- **CORE-D2:** نمای خریدار (۲)، تجهیزات (۴)، کیفیت قانونی و API هاب (۵) به مدارک/گیت‌های واقعی وابسته‌اند. هیچ بازار/پرداختی صرفاً به دلیل نگه‌داشتن نقش فعال نشود.
- **CORE-E1:** نقش تأمین حرفه‌ای (۷) باقی است؛ خریدار خارجی (۹) پنل ندارد؛ قرارداد/صلاحیت قانونی خریدار/صادرکننده و کنترل کیفیت واقعی پیش‌نیاز تجارت باقی‌اند.
- **PR #9:** هسته آزمایشی **in-memory و بدون UI** است؛ این تصمیم باعث نباید تبدیل آن به API واقعی یا فعال‌سازی پردازش داده شخصی شود. بعد از تصویب محدود Scope و Technical، UI فقط از نقشه کاهش‌یافته ساخته شود؛ پنل‌ها و اپ‌های ردشده بازنگردند.
- **حساب/دسترسی:** یک تجربه کاربری مشترک فقط فرض طراحی است، **حق دسترسی خودکار میان Domestic و Export ایجاد نمی‌کند**؛ role/permissionهای واقعی، OAuth/IAM/Consent و امنیت باید در Technical و اسناد معتبر مشخص شوند.
